# 文案规范：把事实写成 HR 三秒能扫完的句子

版式负责「看起来专业」，文案负责「读完想约面」。这一份是文案的打法。

## 一、Bullet 黄金公式

```
**[2～6 字主题词]：** 针对 [具体痛点/场景] ，采用 **[核心方案/工具]** (做了什么动作) ，最终实现 **[量化结果]**
```

四段缺一不可：**主题词 → 痛点 → 动作 → 结果**。

- **主题词**是给 HR 的导航，让他一眼知道这条讲什么。用名词短语，不要用「负责」「参与」。
- **痛点**给出「为什么做」，没有痛点读者就无法判断这件事难不难。
- **动作**是唯一能体现你能力的部分，必须具体到方法、工具、机制。
- **结果**证明你真的做成了。数字最好，没有数字就给业务价值。

单条控制在 **2～3 行（约 45～95 个汉字）**。太短说明没细节，太长说明塞了多件事。

## 二、加粗纪律

只加粗三类东西，每条 bullet **2～4 处**：

1. **专有名词 / 技术栈**：`Redis 多级缓存`、`Elasticsearch 倒排索引`
2. **关键方法 / 机制**：`游标分页`、`延迟双删`、`领域边界拆分`
3. **量化结果**：`P99 从 420ms 降至 130ms`、`成本下降 40%`

不要把整句加粗，不要把动词加粗，不要加粗形容词。加粗太多等于没加粗——HR 的视线会失去落点。

主题词本身就是加粗的（`**慢查询治理：**`），所以它的 2～4 处配额之外还剩 1～3 处给正文。

## 三、概览段怎么写

2～3 行、一段话、不分点。三句话解决三件事：

1. 这个团队/业务是什么、在什么量级上（给背景）
2. 你负责哪一块、独立程度如何（给范围）
3. 宏观上达成了什么（给结果）

> 在交易中台**订单履约组**负责**订单查询链路**的稳定性与性能优化，独立承接 3 个需求，覆盖日均 **800 万**订单的读写路径，实习期结束时接口 P99 从 **420ms 降到 130ms**。

概览段是「电梯陈述」，分点列表是「证据」。先把结论放这里，后面用 bullet 逐条证明。

## 四、反例对照

| ❌ 不要这样写 | ✅ 改成这样 |
| --- | --- |
| 负责后端接口开发 | **接口重构：** 针对订单查询 **P99 420ms** 的问题，把 **N+1 查询**改为**批量预取**，P99 降至 **130ms** |
| 使用了 Redis 缓存 | **缓存设计：** 针对商品详情 **QPS 峰值 3 万** 的场景，设计 **Redis 旁路缓存 + 空值兜底**，数据库 QPS 下降 **78%** |
| 参与了一个电商项目 | **订单模块：** 独立完成下单、取消、退款三条主链路，支撑 **日均 2 万单**，上线三个月 **零 P0 故障** |
| 提升了系统性能 | **慢查询治理：** 把 **慢查询从日均 1200 条压到 40 条**，接口平均耗时降低 **62%** |
| 具有良好的沟通能力和团队协作精神 | （删掉。用事实体现：跨 3 个团队推动接口对齐，把联调周期从 2 周压到 4 天） |
| 熟悉 Java、Python、Go、C++、Rust…… | 按 JD 只留 2～3 门能扛面试的，写清能做什么，而不是罗列名词 |

**一条 bullet 只讲一件事。** 出现「同时」「另外」「以及」的时候，八成该拆成两条。

## 五、动词与量词

- 强动词：设计 / 搭建 / 重构 / 治理 / 定位 / 主导 / 推动 / 落地 / 抽象 / 拆解 / 压降
- 弱动词（尽量换成具体动作）：负责 / 参与 / 协助 / 配合 / 完成了
- 结果表达优先用**前后对比**：`从 X 到 Y`、`降低 N%`、`提升 N 倍`、`覆盖 N 万用户`
- 没有对比数据时用**绝对量级**：`支撑日均 20 万次调用`、`覆盖 12 个业务方`

## 六、专业技能怎么写

```
**[维度名]：** [熟练度动词] **[技能点]**，具备 **[实践能力]**；[熟练度动词] **[延伸技能点]**
```

- 熟练度分三档：**熟悉**（能独立用、能讲清原理）＞ **掌握**（用过、能完成常规任务）＞ **了解**（知道概念）
- 每条 1～2 行，3～5 条。**最重要的维度放第一条**，顺序跟着 JD 走。
- 用中文分号 `；` 切分层级，不要用逗号堆砌。

反例：`熟悉 Java、Python、Go、MySQL、Redis、Kafka、Docker、K8s、Linux、Git、Maven、Spring、Vue……`
——这是关键词仓库，不是技能描述。HR 看不出你会到什么程度，面试官会逐条追问然后发现你只会 hello world。

## 七、应届生 / 没有实习

**不要编造实习。** 没有就换赛道：

1. **项目经历**升为主力，占页面 60% 以上。课程设计、毕设、开源贡献、竞赛项目、自己做的 side project 都算。
2. 项目要有「真实约束」：多少用户、多少数据量、跑了多久、有没有人真的用。哪怕只有 200 个同学用，也是真实数据。
3. **教育经历**里的荣誉行可以承载信息量：GPA 排名、奖学金、竞赛名次、核心课程成绩。
4. 如果项目太薄，用「课程项目」命名，别硬撑成「商业项目」——面试官一眼能看出来。

## 八、JD 对齐（有 JD 时必做）

1. 从 JD 里抽出 **5～8 个关键词**：技术栈、能力项、业务域。
2. 检查简历里这些词是否**自然出现**在 bullet 里（不是硬塞进技能列表）。
3. `headline` 直接写 JD 的岗位名。
4. 技能模块按 JD 权重排序；经历 bullet 的**主题词**优先使用 JD 的原词（JD 说「高并发」，你就别写「大流量」）。
5. 事实不支持的技能**不要写**。对齐是把已有的东西换个说法，不是无中生有。

## 九、版面不满一页时怎么补（重要）

`check` 报出 `pages_estimate` 低于 0.8 时就说明版面在留白。**留白的简历等于告诉 HR「你没做过什么」**，比信息密集的一页差得多。补料按下面的顺序来，**每一步都用已有事实，不许灌水**：

1. **首选：把工作经历里的子系统/模块拆成独立的「项目经历」**。
   一段工作通常做过好几个专项，原来全挤在 4 条 bullet 里。拆出来单独立项，就能把每件事的背景、难点、方案、结果各自展开——用的是同一批事实，只是切分粒度更细。
   > 例：一段「Java 后端工程师」写不满时，把里面的「内容审核后台 0→1」「学习进度服务性能优化」分别提成两条项目经历，各自 3～4 条 bullet。

2. **把经历 bullet 从 3 条补到 4～5 条**。按「背景与难点 / 方案设计 / 落地与结果」拆开写，而不是把一条拉长。

3. **补技能维度**。把 JD 要求、你也确实会用、只是漏写的工具/方法补成第 4、第 5 个维度。

4. **补教育荣誉行**：GPA、排名、奖学金、竞赛、核心课程成绩。

5. **仍然不满一页**：把缺什么列成清单去问用户（具体问「有没有别的项目」「有没有量化的数据」「有没有开源/作品链接」），而不是凑字数。

三条红线：

- 补出来的每一条仍然必须满足「主题词 + 痛点 + 动作 + 结果」，任一段写不出来就不要这条。
- **不许把同一件事换个说法写两遍**（比如工作经历里写了改造订单查询，项目经历里又写一遍同样的内容）。拆项目是换切分维度，不是复制。
- 不要用「复盘」「优化方向」「仍在迭代」这类自我暴露的条目凑版面。

## 十、页数与取舍

一页是默认目标，1～2 页可接受。超了按这个顺序砍：

1. 与目标岗位无关的经历（整段删）
2. 时间最久远、含金量最低的项目
3. 每条经历从 4 条 bullet 砍到 3 条（优先砍结果最弱的）
4. 技能条目从 5 条压到 3 条
5. 概览段从 3 行压到 2 行

**不要**靠缩小字号或压行距来硬塞——版式参数已经在脚本里定死了，动了只会变丑。

## 十、交付前自检

- [ ] 每条 bullet 都有主题词、痛点、动作、结果
- [ ] 每条 bullet 2～4 处加粗，且加粗的是名词/方法/数字
- [ ] 没有「负责」「参与」开头的空话 bullet
- [ ] 数字前后一致（概览段说的和 bullet 里的不能打架）
- [ ] 所有估算数字都进了 `assumed_metrics` 并告知用户
- [ ] 没有编造的公司、职位、时间、证书
- [ ] 技能条目能扛住面试追问
