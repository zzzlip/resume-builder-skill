# 中文简历制作

把「用户的事实」变成「HR 三秒能扫完的一页纸简历」，最后输出 `.docx`。

版式不是让你手搭的：`scripts/build_resume.py` 已经实现了全部视觉规则（斜切色块标题、通栏细线、悬挂缩进 bullet、四列/三列对齐、局部加粗、分级间距）。你的工作是**把事实写成好的文案，填进 JSON**，然后让脚本渲染。手改 .docx 会被下一次生成覆盖，别做。

## 两条路径约定

- **脚本**在 skill 自己的目录下（`scripts/build_resume.py`）。下面命令里的相对路径都相对 skill 目录；不确定时用绝对路径调用，例如 `python3 ~/.claude/skills/resume-builder/scripts/build_resume.py ...`。
- **产物**（`resume.json`、`.docx`、草稿）写在**用户当前的工作目录**，不要写进 skill 目录。

## 四条铁律

1. **不编造经历。** 学校、公司、职位、时间、证书、奖项一律来自用户提供的事实。没有实习经历就不写实习模块——用项目、竞赛、课程设计补位，而不是凭空造一段大厂实习。这一条破了，简历就成了废纸，还会在面试里当场露馅。
2. **量化数据分两种。** 用户给了数字就用用户的，不许改口径、不许放大。用户没给，可以按场景写一个保守、合理、被追问时能解释得通的数字——但必须在草稿里单独列出来请用户确认（`assumed_metrics`）。「没有数字」从来不是编造数字的理由，只是允许有依据地估算。
3. **先给草稿，不要直接出 Word。** 用户要在文字层面拍板。跳过确认直接生成，返工成本极高。
4. **一条 bullet 只说一件事。** 塞了两三件事就拆开。这条决定了 HR 扫读时能不能抓住重点。

## 工作流

### 0. 先搞清楚手上有什么

用户可能给：目标岗位 JD、现有简历文件（docx/pdf/txt）、零散的经历笔记、或者只有一句「帮我做个简历」。

- 有 `.docx` 简历 → `python3 scripts/read_docx_text.py 旧简历.docx` 取全文，不要靠猜。
- 有 PDF → 用手上可用的 PDF 解析工具读，或者让用户直接贴文本。
- 有 JD → 先抽关键词（见 `references/writing.md` 的「JD 对齐」）。
- 什么都没有 → 按下面的清单问，一次问完，别挤牙膏。

必问清单（缺哪项问哪项，用户已经说过的不要再问）：

> 姓名 / 手机 / 邮箱 / 城市 / 可附的链接（GitHub、作品集、博客）
> 目标岗位（或 JD）
> 教育：学校、专业、学历、起止时间、GPA 或排名、奖学金与竞赛
> 实习/工作：公司、岗位、起止时间、团队在做什么、你具体做了什么
> 项目：名称、你的角色、起止时间、要解决什么问题、你做了哪几件事
> 技能：语言/框架/工具/证书，各自到什么程度

一次问 4 个问题以内，用选项化的问法降低回答成本。问不到的字段就留空，不要填「暂无」。

### 1. 写 `resume.json`

字段定义、必填项、渲染映射见 `references/schema.md`；文案怎么写见 `references/writing.md`。

在用户当前工作目录下创建 `resume.json`。**不要**在 JSON 里写 Markdown 标题或列表符号——结构由字段表达，只有**加粗**用 `**文字**`。

### 2. 自检

```bash
python3 scripts/build_resume.py check resume.json
```

输出是 JSON：`errors` 必须清零（脚本会拒绝生成），`warnings` 逐条判断——是内容问题就改，是误报就跳过。重点看 `pages_estimate`：

- **> 2.0** → 必须删，按 `references/writing.md` 第九节的取舍顺序砍。
- **1.0 ～ 2.0** → 可接受；能压到一页更好。
- **< 0.8** → **版面在留白，不要就这么交付。** 按 `references/writing.md`「版面不满一页时怎么补」补齐，首选把工作经历里的子系统/模块拆成独立的「项目经历」条目，其次把 bullet 补到 4～5 条、补技能维度、补教育荣誉。补的全是已有事实，不是灌水；实在补不出来就把缺的素材列成清单去问用户。

### 3. 预览，然后停下来

```bash
python3 scripts/build_resume.py preview resume.json
```

把输出**原样贴给用户**（不要转述、不要摘要），再用两三句话说明：这次做了什么判断、哪些数据是估算的、哪几处建议他补充。然后**等用户确认**。

### 4. 生成 Word

```bash
python3 scripts/build_resume.py build resume.json -o 简历-张三.docx
```

可选参数：`--theme 1F3864`（主题色）、`--cjk-font 微软雅黑`、`--latin-font Calibri`、`--slant forward|back`（斜切方向）。

### 5. 交付

给出 `.docx` 的**绝对路径**，并简述：几个模块、估算页数、还剩哪些待补信息。如果环境里有 LibreOffice 或 Word，顺手渲染一页给用户看：

```bash
soffice --headless --convert-to pdf 简历.docx && pdftoppm -jpeg -r 120 简历.pdf page
```

没有渲染器就跳过，不要因为看不了图就反复折腾——脚本的版式是确定的。

## 版式（已由脚本固化，这里是让你能向用户解释）

单栏纵向，A4，左右边距 2.0cm，正文 10.5pt / 行距 14pt。

| 元素 | 规则 |
| --- | --- |
| 姓名 | 20pt 加粗主题色，右侧右对齐「求职意向」 |
| 联系方式 | 9.5pt 灰色，`·` 分隔的单行 |
| 模块标题 | 左侧 3.6cm 主题色右斜切色块 + 白色 11pt 加粗标题，色块底部向右延伸一条通栏 0.5pt 浅灰线 |
| 教育/经历/项目 标题行 | 三列或四列，前三项加粗，最右侧时间 9pt 灰色右对齐 |
| 列表 | 实心 `•`，悬挂缩进 0.6cm（折行与首行文字左对齐，不与圆点对齐） |
| 加粗 | 只加粗专有名词、方法/工具、量化结果；模块标题白字是唯一例外 |
| 间距 | bullet 内紧凑、bullet 之间 2pt、经历之间 6pt、模块之间 12pt |

主题色默认深藏蓝 `#1F3864`。换色时脚本会自动判断白字还是黑字更清楚，不用你操心。

## 什么时候该反问

- 用户给的经历只有一句「负责后端开发」→ 追问：什么业务、什么量级、你改了什么、结果如何。**没有细节就写不出好 bullet，宁可多问一轮。**
- 用户要求写明显不实的经历（挂名、夸大职级、编造公司）→ 直接说明不做，并给出替代写法（把课程项目写成项目经历、把个人作品写成作品集）。
- 用户抱怨「太丑」但说不清要什么 → 先给默认版式，再问要不要换主题色/斜切方向。

## 文件

- `scripts/build_resume.py` — 唯一的渲染器，纯标准库，零依赖
- `scripts/read_docx_text.py` — 从 .docx 抽纯文本，用于重构旧简历
- `references/schema.md` — resume.json 字段表与完整示例
- `references/writing.md` — Bullet 公式、加粗规则、反例、JD 对齐
